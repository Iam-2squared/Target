# Two-player soccer database contract

The separate `/workspace/2player` application verifies a KGS common login on its server, then calls `public.two_player_rpc(secret, action, input)`. The dedicated secret belongs only on that server. Its SHA-256 hash is provisioned separately in `target_private.two_player_credentials`; this migration contains neither a secret nor a financial correction manifest. Existing Target gambling RPCs remain disabled.

The migrations were created with Supabase CLI `migration new target_two_player_soccer` and `migration new target_two_player_soccer_formations_v2`. The first adds the soccer mechanism and minimally extends the reviewed wallet projection. The V2 follow-up adds eight pieces per side and three starting formations, preserving all V1 receipts and financial rules. Its cutover refuses existing waiting or playing rooms; finish or cancel/refund them before applying it. Terminal V1 history remains unchanged.

All actor fields come from the verified KGS identity. Every call supplies `memberId` (UUID) and `name` (1–20 characters). Mutations also supply a fresh UUID `requestId`. Reusing an accepted request ID with different content returns `409 REQUEST_CONFLICT`; an exact retry returns the current wallet and match without repeating the action.

| Action | Additional input | Behavior |
| --- | --- | --- |
| `wallet` | None | Current shared wallet and reserved stake |
| `list` | None | This member's latest 20 rooms, active rooms first; no global room directory |
| `create` | `stake` | Create a private six-character room code |
| `join` | `code` | Join an available room using its code |
| `offer` | `matchId` or `code`, `stake` | Change the actor's offer and clear both confirmations |
| `formation` | `matchId` or `code`, integer `formation: 0..2` | Select the actor's starting formation before funding and clear both confirmations |
| `ready` | `matchId` or `code`, `ready` boolean | Confirm the matching offers; the second confirmation funds both stakes atomically |
| `state` | `matchId` or `code` | Resume an owned match; may claim a pending calculation for the trusted server |
| `input` | `matchId` or `code`, `round`, `version: 2`, integer `piece: 0..7`, integer `angle: 0..359`, integer `power: 0..100` | Lock one owned piece's shot on the active player's turn |
| `resolve` | `matchId` or `code`, `round`, `version: 2`, `claimToken`, `goal`, `state`, `frames` | Trusted server commits the deterministic physics result |
| `cancel` | `matchId` or `code` | Cancel before funding, or request mutual cancellation after funding |
| `expire` | None | Expire this member's idle match without funding anything |

Success returns `{ok:true,wallet,match? ,rooms?}`. Errors use the existing `{error:{status,code,message}}` convention. Wallet fields are `balance`, `totalIncome`, `spent`, `walletRevision`, `gameNet`, and `escrow`. The existing identity `balance + spent = totalIncome` remains exact. `balance` excludes the reserved stake; `escrow` is that member's reserved stake. Match `escrow` is the full two-player pot. Match `winner` is `host`, `guest`, `draw`, or null. A room's `stake` remains null until both players confirm.

Gameplay uses alternating turns. A server-generated random bit selects the first player when both stakes are reserved. The database accepts input only from `match.turn`, and the selected piece is immutable once accepted. One accepted shot produces a private `_processing` claim containing `claimToken`, `matchId`, `round`, `version`, `turn`, `state`, `formations:[hostFormation,guestFormation]`, and `inputs:{host,guest}` with each input containing `piece`, `angle`, and `power`. The inactive input always has piece zero and zero power. The claim lasts ten seconds; a later `state` call can reclaim an abandoned calculation. A stale token cannot resolve. The application server must remove `_processing` from browser responses and never expose a browser route for `resolve`.

The physics result is independent of connection latency. Physics version 2 uses a 640×960 field and 16 player points: host pieces 0–7 first, then guest pieces 0–7. Each team has one goalkeeper and seven field pieces. Formations 0, 1, and 2 arrange those field pieces as 3–3–1, 2–3–2, and 2–2–3. `target_private.two_player_initial_state(hostFormation,guestFormation)` defines the exact canonical coordinates; guest coordinates mirror host coordinates as `(640-x,960-y)`, and the ball starts at `(320,480)`. Both formations default to zero. The second funding confirmation initializes the chosen pair. The trusted server simulates the selected owned piece and commits `goal: "host" | "guest" | null`, final `state`, and replay `frames`. On a goal, both `match.state` and the physics outcome's `lastRound.state` reset to the chosen formations; `lastRound.frames` retains the goal entry for animation. Every resolved shot flips the turn. Three goals wins; reaching 40 shots without a three-goal winner draws and refunds both stakes. Resolved inputs and results are permanent, and identical result retries cannot create another payout. Every match update advances `updatedAt` by at least one microsecond so clients can reject stale formation or confirmation responses.

Both offers must be at least 100 轟 in steps of 100; there is no game-specific maximum. The shared wallet's existing 10,000,000,000,000-轟 representability limit, available balance and settlement headroom still apply. Offers, stakes, escrow and wallet-event deltas use PostgreSQL bigint; a two-player pot can be twice the offered amount. Creating, joining, offering, listing, polling, and the first confirmation never reserve money. The second explicit confirmation validates both balances before either debit. Reservation appends a `-stake` event for each player and subtracts exactly that amount from `profiles.total_points` and `casino_net`. Settlement appends either `2*stake` to the winner and zero to the loser, or `stake` to each player on a draw/cancellation. Every event is append-only and unique by match, member, and reserve/settlement phase. Neither `spent_points` nor gacha ownership changes. The existing wallet revision trigger applies to each nonzero financial change.

Every financial action uses the existing global advisory lock `991101`. For every match, `sum(two_player_wallet_events.delta) + match.escrow = 0`. The finance projection's games component adds these deltas exactly once alongside the old immutable casino receipts. Existing source voids, external source recoveries, income corrections, full/partial receipt write-offs, inventory tombstones, and restoration audits remain intact. Shared wallets retain enough upper-bound headroom for any outstanding soccer payout.

After funding, either player may request cancellation, and both requests refund both players. An unresolved match expires ten minutes after its last accepted input, resolution, offer, join, or confirmation. Polling and repeated inputs do not prolong the deadline. Expiry cancels and refunds; it never awards a latency-based win. Confirmed winners cannot be undone by expiry. `target_private.two_player_expire(NULL,100)` processes up to 100 expired matches, and a conditional `pg_cron` installation schedules it once per minute where the extension is available. Plain local PostgreSQL skips the optional extension. The private cron function needs no new storage to refund.

All new tables have RLS and explicit revokes from `PUBLIC`, `anon`, `authenticated`, and `service_role`. Only the credential-gated public RPC is executable by API roles. Credential checks run before input parsing, rate allocation, locks, or expiry. New identities respect Target's existing 500-profile ceiling; existing members can still resume and refund at that ceiling. Each member is limited to one active match, 240 calls per minute, 20 created rooms per UTC day, and 256 ordinary accepted mutation receipts per match. JSON inputs, physics state, replay samples, and result bytes are bounded.

The existing 100 MiB logical storage ceiling covers this feature. A new match reserves 16,384 bytes for its bounded match/participant/finance records and two cancellation receipts. Ordinary request receipts reserve 512 bytes; rate slots reserve 256 bytes. Each accepted V2 shot reserves 393,216 bytes so its result can finish even if another operation consumes the remaining capacity. Result input is limited to 393,216 bytes, with replay frames limited to 360,448 bytes of JSONB. Resolution replaces that reservation with `2048 + pg_column_size(frames) + pg_column_size(state)`, including the result receipt. Cancelling a pending shot releases all but 1,024 bytes for its immutable input, using its actual reservation rather than a version-specific constant. Rate slots expire after a day; permanent finance/input/request receipts remain. Refunding and first resolution need no fresh quota allocation.

Historical wallet restoration is refused for a member with funded active soccer escrow. It also refuses a historical cutoff between that member's reserve and settlement events, including a match that has already finished, because that would restore a debit without its corresponding escrow. Cancel/refund active matches and choose a cutoff before reservation or after settlement. Existing explicit current-time income corrections with `cutoff_at = prepared_at` continue to work; no automatic money adjustment is introduced.

For verification, run the local-only `/workspace/2player/tests/e2e-soccer.cjs` harness and the read-only `supabase/tests/two_player_soccer_verify.sql` postflight. The harness requires `NODE_ENV=test`, a loopback-only disposable PostgreSQL database, and synthetic identities. It never accepts a hosted database URL.

## Online opponents and FIFO matchmaking

`20261109221928_target_two_player_matchmaking.sql` adds a separate `public.two_player_lobby_rpc(secret, action, input)` using the existing dedicated soccer credential. It does not replace the soccer RPC, financial projection, settlement, source integration, or retired gambling functions. Existing active and historical matches remain unchanged. Room codes remain an internal compatibility field; new clients choose opponents and resume by match ID.

Every lobby action receives `memberId`, `name`, and `sessionId` from the trusted server after KGS identity verification. `sessionId` is a server-derived HMAC digest of the opaque KGS session, never the token itself. The browser cannot supply those actor fields. Mutations also require a UUID `requestId`. Their hash excludes display name and session metadata, so a successful intent can be checked after a rename or re-login without changing its meaning.

| Lobby action | Additional input | Result |
| --- | --- | --- |
| `snapshot` | None | Online opponents, pending invitations, own queue position, shared wallet, and own active match summary |
| `heartbeat` | None | Refresh this session's presence, then return the snapshot |
| `leave` | None | Mark only this session offline; remove queued/invited state if no other session is online |
| `logout` | None | Internal server action that permanently fences the logging-out session before KGS token revocation |
| `challenge` | `requestId`, `targetId`, `stake`, `formation` | Invite a specific online, available user using the sender's preselected settings |
| `accept` | `requestId`, `invitationId`, `stake`, `formation` | Recipient accepts and retains their own preselected settings |
| `decline` | `requestId`, `invitationId` | Recipient declines an incoming invitation |
| `invite_cancel` | `requestId`, `invitationId` | Sender cancels their outgoing invitation |
| `queue` | `requestId`, `stake`, `formation` | Join the random queue, pairing the oldest available users first |
| `queue_cancel` | `requestId` | Leave the random queue |

Snapshots return `lobby:{online:[{memberId,name,busy}],queue:{joinedAt,position,stake,formation}|null,incoming:[],outgoing:[]}`. Incoming entries include `id`, `from:{memberId,name}`, `stake`, `formation`, `createdAt`, and `expiresAt`; outgoing entries use `to` instead of `from`. Online results contain at most 100 other users. An active match is a bounded summary without replay frames; the existing game endpoint owns full replay and processing recovery.

Presence expires 60 seconds after a heartbeat. Clients normally heartbeat every 20 seconds while visible. Presence is tracked separately for each session, so leaving one device does not remove a user active on another. Logout tombstones last eight days, exceeding the KGS token's seven-day lifetime; a heartbeat verified before logout cannot restore that revoked session. Existing-session leave/logout cleanup bypasses ordinary wallet polling limits. The snapshot does not extend presence by itself.

Invitations expire after 60 seconds, allow one outgoing request per sender and at most five incoming per recipient, and never charge or reserve funds. They do not prevent the recipient from joining a random game. Accepting an invitation and random matching serialize through the existing global lock `991101`; only one can claim either user. Pairing clears both users' queued and pending invitation state. Offline users, insufficient queue balances, and users already in an active match are removed from matchmaking eligibility.

The random queue is global, not separated by stake. Its database sequence defines FIFO order. The oldest user pairs with the oldest eligible opponent. If one player has exhausted the existing host-only limit of 20 created matches per UTC day, the other eligible player becomes the internal host while preserving both players' settings. Two host-ineligible users wait for an eligible counterpart without blocking later eligible pairings. Queue settings are fixed until cancellation; an exact retry keeps the original place.

Match creation calls the unchanged soccer `create`, `join`, and necessary `offer`/`formation` actions within one transaction. A JSON error from any wrapped call raises a private SQL exception caught only by the outer lobby RPC, rolling back the whole attempted pair before returning the error. The resulting match is still unfunded. Both players must explicitly confirm matching stakes through the existing ready flow. There is no automatic wallet debit, payout, or change to the eight-piece physics.

Accepted lobby mutation receipts are permanent and hashed. Retrying an old queued or invitation request returns the current snapshot instead of reenqueuing, reinviting, or creating another match. Ephemeral presence, queue, and invitation rows are separately bounded and reclaimed. Each session and queue row reserves 512 logical bytes, an invitation reserves 1,024, a reusable rate row reserves 256, and a permanent request receipt reserves 512. All allocations use the existing 100 MiB ceiling, with exact releases on deletion. Expired ordinary sessions are removed after a day; revoked sessions remain for eight days. Requests are limited to 30 new mutations per minute, 1,000 per UTC day, and 20 challenge attempts per day. Actual cancellation/decline operations may free existing resources after ordinary mutation limits are exhausted; empty repeated release spam does not bypass those limits.

All new tables use private-schema RLS and explicit API-role revokes. Only the credential-gated public lobby RPC is exposed. Check `supabase/tests/two_player_lobby_verify.sql` after deployment, and run the local-only `tests/e2e-matchmaking.cjs` harness against synthetic identities and a disposable loopback database for concurrency and end-to-end behavior.
